# Path with minimum effort

**Difficulty:** Hard  ·  **Topic:** Graphs [Concepts & Problems] › Shortest Path Algorithms and Problems

## Problem
You are given a `rows x cols` grid `heights` where `heights[r][c]` is the elevation of that cell. You start at the top-left cell `(0,0)` and want to reach the bottom-right cell `(rows-1, cols-1)`, moving up, down, left or right. The **effort** of a route is the maximum absolute height difference between any two consecutive cells on it. Return the minimum effort over all routes.

```
Input:  heights = [[1,2,2],
                   [3,8,2],
                   [5,3,5]]
Output: 2
```
The route `1 → 2 → 2 → 2 → 5` down the right side has consecutive differences `1, 0, 0, 3`... but the better route `1 → 3 → 5 → 3 → 5` has differences `2, 2, 2, 2`, so its effort is 2. Any route through the `8` costs at least 5, and the right-hand route ends with `|2-5| = 3`.

## Approach 1: Explore every path (brute force)
DFS/backtracking over all simple paths, tracking the running maximum difference and keeping the best. Exponentially many paths in a grid — hopeless beyond tiny inputs, but it makes the objective clear: we minimise a **maximum**, not a sum.

- **Time:** exponential
- **Space:** O(rows·cols) recursion

## Approach 2: Binary search on the answer + BFS feasibility check
The predicate "can I reach the end using only steps of difference ≤ `X`?" is monotone: if it holds for `X`, it holds for every larger value. So binary search `X` over `0 .. maxHeightDiff` and test each candidate with a BFS/DFS that only walks edges with difference ≤ `X`. Clean and easy to reason about.

- **Time:** O(rows·cols·log(maxDiff))
- **Space:** O(rows·cols)

## Approach 3: Dijkstra with "max edge" instead of "sum of edges" (Optimal)

**Key observation.** Dijkstra is usually described for path *sums*, but its correctness argument only needs the path cost to be **monotone non-decreasing as the path grows** — extending a path must never make it cheaper. The cost "maximum edge difference along the path" satisfies that: adding another step keeps the max the same or raises it, never lowers it. So the greedy invariant survives, and we can run Dijkstra with the combination rule

```
cost(path + edge) = max(cost(path), |height difference of edge|)
```

instead of the usual `cost + weight`. This variant is often called the **minimax path** or bottleneck shortest path.

**Algorithm.**
1. Keep a grid `effort[r][c]` = the smallest known "max difference" needed to reach `(r,c)`, initialised to infinity; `effort[0][0] = 0`.
2. Push `(0, 0, 0)` = `(effort, row, col)` into a min-heap keyed by effort.
3. Pop the cell with the smallest effort. If it is the destination, return that effort — the greedy invariant says nothing cheaper can arrive later.
4. Otherwise, for each of the four neighbours compute `newEffort = max(currentEffort, |h[nr][nc] - h[r][c]|)`. If it beats the recorded `effort[nr][nc]`, update and push.
5. If the heap empties, the destination is unreachable (cannot happen on a full grid).

**Why popping is final.** Suppose we pop `(e, u)` and some other route to `u` had effort `e' < e`. That route leaves the settled region through some cell `x` still in the heap, and the effort of its prefix up to `x` is at most `e'` — but every heap entry has key ≥ `e`, so `e' >= e`, contradiction. Exactly the standard Dijkstra argument, using only monotonicity.

**Dry run** on the example:
- Start `(0,0)` with effort 0. Neighbours: right `(0,1)` costs `|1-2| = 1`; down `(1,0)` costs `|1-3| = 2`. Heap: `{(1,(0,1)), (2,(1,0))}`.
- Pop `(1,(0,1))`. Right `(0,2)`: `max(1, |2-2|) = 1`. Down `(1,1)`: `max(1, |2-8|) = 6`. Heap: `{(1,(0,2)), (2,(1,0)), (6,(1,1))}`.
- Pop `(1,(0,2))`. Down `(1,2)`: `max(1, |2-2|) = 1`. Heap gains `(1,(1,2))`.
- Pop `(1,(1,2))`. Down `(2,2)`: `max(1, |2-5|) = 3`. Heap: `{(2,(1,0)), (3,(2,2)), (6,(1,1))}`.
- Pop `(2,(1,0))`. Down `(2,0)`: `max(2, |3-5|) = 2`. Right `(1,1)`: `max(2,|3-8|) = 5`, improving 6.
- Pop `(2,(2,0))`. Right `(2,1)`: `max(2, |5-3|) = 2`. Pop `(2,(2,1))`. Right `(2,2)`: `max(2, |3-5|) = 2`, which improves the earlier 3 → push `(2,(2,2))`.
- Pop `(2,(2,2))` — destination → answer **2** ✓. Notice the first route to the destination cost 3 and was later improved; the heap ordering guarantees we only *return* once the value is provably minimal.

- **Time:** O(rows·cols·log(rows·cols))
- **Space:** O(rows·cols) for the effort grid and the heap

*(A Union-Find alternative sorts all edges by difference and unions them until `(0,0)` and the last cell are connected; the last edge added is the answer — also a fine O(E log E) solution.)*

## Code (Optimal)

### C++
```cpp
#include <vector>
#include <queue>
#include <cmath>
#include <climits>
using namespace std;

class Solution {
public:
    int minimumEffortPath(vector<vector<int>>& heights) {
        int n = heights.size(), m = heights[0].size();
        vector<vector<int>> effort(n, vector<int>(m, INT_MAX));
        // {effort, row, col}
        priority_queue<tuple<int,int,int>, vector<tuple<int,int,int>>, greater<>> pq;
        effort[0][0] = 0;
        pq.push({0, 0, 0});

        int dr[4] = {-1, 1, 0, 0};
        int dc[4] = {0, 0, -1, 1};

        while (!pq.empty()) {
            auto [e, r, c] = pq.top(); pq.pop();
            if (r == n - 1 && c == m - 1) return e;   // popped => final
            if (e > effort[r][c]) continue;           // stale entry
            for (int k = 0; k < 4; k++) {
                int nr = r + dr[k], nc = c + dc[k];
                if (nr < 0 || nr >= n || nc < 0 || nc >= m) continue;
                int ne = max(e, abs(heights[nr][nc] - heights[r][c]));
                if (ne < effort[nr][nc]) {
                    effort[nr][nc] = ne;
                    pq.push({ne, nr, nc});
                }
            }
        }
        return 0;   // single-cell grid
    }
};
```

### Java
```java
import java.util.*;

class Solution {
    public int minimumEffortPath(int[][] heights) {
        int n = heights.length, m = heights[0].length;
        int[][] effort = new int[n][m];
        for (int[] row : effort) Arrays.fill(row, Integer.MAX_VALUE);

        // {effort, row, col}
        PriorityQueue<int[]> pq = new PriorityQueue<>(Comparator.comparingInt(a -> a[0]));
        effort[0][0] = 0;
        pq.add(new int[]{0, 0, 0});

        int[] dr = {-1, 1, 0, 0};
        int[] dc = {0, 0, -1, 1};

        while (!pq.isEmpty()) {
            int[] cur = pq.poll();
            int e = cur[0], r = cur[1], c = cur[2];
            if (r == n - 1 && c == m - 1) return e;
            if (e > effort[r][c]) continue;
            for (int k = 0; k < 4; k++) {
                int nr = r + dr[k], nc = c + dc[k];
                if (nr < 0 || nr >= n || nc < 0 || nc >= m) continue;
                int ne = Math.max(e, Math.abs(heights[nr][nc] - heights[r][c]));
                if (ne < effort[nr][nc]) {
                    effort[nr][nc] = ne;
                    pq.add(new int[]{ne, nr, nc});
                }
            }
        }
        return 0;
    }
}
```

### Python
```python
import heapq
from typing import List

class Solution:
    def minimumEffortPath(self, heights: List[List[int]]) -> int:
        n, m = len(heights), len(heights[0])
        INF = float("inf")
        effort = [[INF] * m for _ in range(n)]
        effort[0][0] = 0
        pq = [(0, 0, 0)]                       # (effort, row, col)
        moves = ((-1, 0), (1, 0), (0, -1), (0, 1))

        while pq:
            e, r, c = heapq.heappop(pq)
            if (r, c) == (n - 1, m - 1):
                return e
            if e > effort[r][c]:
                continue
            for dr, dc in moves:
                nr, nc = r + dr, c + dc
                if 0 <= nr < n and 0 <= nc < m:
                    ne = max(e, abs(heights[nr][nc] - heights[r][c]))
                    if ne < effort[nr][nc]:
                        effort[nr][nc] = ne
                        heapq.heappush(pq, (ne, nr, nc))
        return 0
```

## Key Takeaways
- This is a **minimax (bottleneck) path** problem: minimise the largest single step, not the total.
- Dijkstra generalises beyond sums — swap `cost + w` for `max(cost, w)`; correctness only needs the cost to be non-decreasing as the path extends.
- Return when the destination is *popped*, not when first assigned: a cheaper route can still arrive (as it does in the dry run, 3 → 2).
- Alternatives with the same answer: binary search on the effort with a reachability BFS, or Union-Find adding edges in increasing difference order.
