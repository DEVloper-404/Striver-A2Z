# Maximum XOR of two numbers in an array

**Difficulty:** Hard  ·  **Topic:** Tries › Problems

## Problem
Given an array of non-negative integers `nums`, return the maximum value of `nums[i] ^ nums[j]` over all pairs `(i, j)`.

```
Input:  nums = [3, 10, 5, 25, 2, 8]
Output: 28
```
The best pair is `5 ^ 25 = 00101 ^ 11001 = 11100 = 28`.

## Approach 1: Check every pair (Brute Force)

Two nested loops over all pairs, tracking the maximum XOR. Perfectly correct and worth stating as the baseline, but with `n` up to `2·10^5` this is `4·10^10` operations.

- **Time:** O(n^2)
- **Space:** O(1)

## Approach 2: Binary trie with a greedy descent (Optimal)

**Observation 1 — maximise from the most significant bit.** XOR compares numbers bit by bit, and a single high bit dominates every lower bit combined (`2^k > 2^{k-1} + ... + 2^0`). So to maximise `x ^ y`, walk the bits from the top down and take a `1` in the result whenever one is reachable; never sacrifice a high bit hoping to win lower ones.

**Observation 2 — "reachable" means a partner with the opposite bit exists.** At bit `i`, if `x` has bit `b`, the XOR bit is `1` exactly when the partner `y` has bit `1 - b`. So the question at every level is only: "among the partners still compatible with my choices so far, does any have bit `1 - b` here?"

**Observation 3 — a binary trie answers that in O(1) per level.** Store every number as a path of fixed-width bits (MSB first) in a trie whose nodes have two children, `0` and `1`. Being at a node after `k` steps means "the set of stored numbers whose top `k` bits match the path I took". Asking whether a compatible partner has bit `1 - b` next is just asking whether `links[1 - b]` is non-null.

**The algorithm.**
1. Build a binary trie and insert every number, walking bits `30` down to `0` (enough for values below `2^31`) and creating missing children.
2. For each `x` in `nums`, descend from the root:
   - `b = (x >> i) & 1`, `want = 1 - b`.
   - If `links[want]` exists, set bit `i` of the running answer and move there.
   - Otherwise move to `links[b]` (forced; that XOR bit will be 0).
3. Track the maximum over all `x`.

Inserting everything up front means each query may pair `x` with itself, giving `0`; that never beats the true maximum whenever `n >= 2`, so no special handling is needed.

**Dry run on `nums = [3,10,5,25,2,8]`** using 5 bits: `3=00011`, `10=01010`, `5=00101`, `25=11001`, `2=00010`, `8=01000`. Insert all, then query `x = 25 = 11001`.

- **bit 4:** `x` has `1`, so we want a partner with `0`. Numbers with bit 4 = 0 are `{3,10,5,2,8}` → the `0` child exists. Take it; answer bit 4 = **1**. Surviving partners: `{3,10,5,2,8}`.
- **bit 3:** `x` has `1`, want `0`. Among the survivors, bit 3 is `0` for `{3,5,2}` and `1` for `{10,8}` → the `0` child exists. Take it; answer bit 3 = **1**. Survivors: `{3,5,2}`.
- **bit 2:** `x` has `0`, want `1`. Bit 2 is `1` only for `5` (`00101`) → child exists. Take it; answer bit 2 = **1**. Survivors: `{5}`.
- **bit 1:** `x` has `0`, want `1`. `5` has bit 1 = `0`, so the `1` child is absent → forced to `0`; answer bit 1 = **0**.
- **bit 0:** `x` has `1`, want `0`. `5` has bit 0 = `1`, so the `0` child is absent → forced; answer bit 0 = **0**.

Result `11100 = 28`, and the descent narrowed the candidate set from six numbers to exactly the optimal partner `5` in three steps. Querying the other five numbers never exceeds 28, so the answer is **28**.

- **Time:** O(n · B) with `B = 31` bit levels — linear in practice
- **Space:** O(n · B) trie nodes

## Code (Optimal)

### C++
```cpp
#include <vector>
#include <algorithm>
using namespace std;

class Solution {
    struct Node { Node* links[2] = {nullptr, nullptr}; };

    static const int B = 30;                     // bits 30..0 cover values < 2^31

    void insert(Node* root, int num) {
        Node* cur = root;
        for (int i = B; i >= 0; i--) {
            int bit = (num >> i) & 1;
            if (cur->links[bit] == nullptr) cur->links[bit] = new Node();
            cur = cur->links[bit];
        }
    }

    int queryMax(Node* root, int num) {
        Node* cur = root;
        int best = 0;
        for (int i = B; i >= 0; i--) {
            int bit = (num >> i) & 1;
            int want = 1 - bit;                  // opposite bit -> XOR bit is 1
            if (cur->links[want] != nullptr) {
                best |= (1 << i);
                cur = cur->links[want];
            } else {
                cur = cur->links[bit];           // forced, XOR bit stays 0
            }
        }
        return best;
    }

public:
    int findMaximumXOR(vector<int>& nums) {
        if (nums.size() < 2) return 0;
        Node* root = new Node();
        for (int x : nums) insert(root, x);

        int answer = 0;
        for (int x : nums) answer = max(answer, queryMax(root, x));
        return answer;
    }
};
```

### Python
```python
from typing import List

class Solution:
    def findMaximumXOR(self, nums: List[int]) -> int:
        if len(nums) < 2:
            return 0

        B = 30                                   # bits 30..0 cover values < 2^31
        root = [None, None]                      # a node is [child0, child1]

        for num in nums:
            cur = root
            for i in range(B, -1, -1):
                bit = (num >> i) & 1
                if cur[bit] is None:
                    cur[bit] = [None, None]
                cur = cur[bit]

        answer = 0
        for num in nums:
            cur = root
            best = 0
            for i in range(B, -1, -1):
                bit = (num >> i) & 1
                want = 1 - bit                   # opposite bit -> XOR bit is 1
                if cur[want] is not None:
                    best |= (1 << i)
                    cur = cur[want]
                else:
                    cur = cur[bit]               # forced, XOR bit stays 0
            answer = max(answer, best)

        return answer
```

## Key Takeaways
- Greedy from the MSB is optimal for XOR because one high bit outweighs all lower bits together; the trie just makes "is the opposite bit available?" an O(1) lookup.
- A trie node after `k` steps represents the set of numbers sharing those top `k` bits, which is why the descent prunes candidates without ever enumerating them.
- Pad all numbers to the same bit width (31 or 32) so paths align; a shorter path would compare mismatched bit positions.
- Edge cases: fewer than two elements → 0; duplicates and self-pairing give XOR 0 and are harmless. An alternative O(n·B) solution builds the answer bit by bit with a hash set of prefixes.
