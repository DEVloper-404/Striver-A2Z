# Prefix to Postfix Conversion

**Difficulty:** Medium  ·  **Topic:** Stack and Queues [Learning, Pre-In-Post-fix, Monotonic Stack, Implementation] › Prefix, Infix, PostFix Conversion Problems

## Problem
Given a valid **prefix** expression (operator written before its two operands), produce the equivalent **postfix** expression (operator written after its two operands). Neither notation uses brackets. Operands are single characters; operators are `+ - * / ^`.

```
Input:  *+ab-cd
Output: ab+cd-*
```
Both encode the tree `*( +(a, b), -(c, d) )`, i.e. `(a+b)*(c-d)`.

## Approach 1: Recursive descent
Parse the prefix string with a moving index: if the current character is an operand, consume it and return it; if it is an operator, recursively parse `left`, then `right`, and return `left + right + op`. This is essentially a pre-order read of the expression tree that emits a post-order string, and it reads very naturally. The catch is stack depth — a chain like `+a+b+c+de` recurses `n/2` levels deep — and the shared index must be passed by reference, a common source of bugs.

- **Time:** O(n) character visits
- **Space:** O(n) recursion depth.

## Approach 2: Right-to-left scan with a stack (Optimal)
In a prefix string an operator's operands lie **to its right**, so if we scan from the right end we always meet both operands before the operator that needs them. That is exactly the condition for a stack-based one-pass conversion.

Invariant: at any point in the backwards scan, the stack holds the already-converted postfix strings of every complete sub-expression to the right of the current position, with the leftmost such sub-expression on top.

Scan right to left:

1. **Operand** → push it as a one-character string (a single operand is already valid postfix).
2. **Operator `op`** → pop once to get `left` (the top is the sub-expression nearest to the operator, i.e. its *first* operand), pop again to get `right`. Push `left + right + op`, which is postfix by definition.
3. When the scan ends, the only string left on the stack is the answer.

**Why concatenation is safe without brackets.** Postfix is self-delimiting: scanning it left to right, each operator consumes the two most recently completed values, and that parse is unique. So gluing two valid postfix strings and appending an operator always yields a valid postfix string denoting the intended combination — precedence never enters the picture.

**Watch the pop order.** Prefix scans backwards, so the first pop is the **left** operand — the opposite of the postfix-source conversions, where the first pop is the right one. Using the wrong order turns `-cd` into `dc-` = `d - c`.

**Dry run on `*+ab-cd`:**

| Read (right → left) | Action | Stack (bottom → top) |
|---|---|---|
| `d` | push | `d` |
| `c` | push | `d`, `c` |
| `-` | left=`c`, right=`d` → `cd-` | `cd-` |
| `b` | push | `cd-`, `b` |
| `a` | push | `cd-`, `b`, `a` |
| `+` | left=`a`, right=`b` → `ab+` | `cd-`, `ab+` |
| `*` | left=`ab+`, right=`cd-` → `ab+cd-*` | `ab+cd-*` |

A second check on a right-heavy input: `-a+bc` (meaning `a - (b + c)`) gives `c`, `b` pushed, then `+` → `bc+`, then `a` pushed, then `-` → left=`a`, right=`bc+` → `abc+-`. Evaluating that postfix indeed computes `a - (b + c)`. ✓

- **Time:** O(n) stack operations; O(n^2) overall in the worst case from repeated string concatenation.
- **Space:** O(n) stack entries, up to O(n^2) characters held in the worst case.

## Code (Optimal)

### C++
```cpp
#include <string>
#include <stack>
#include <cctype>
using namespace std;

class Solution {
public:
    string prefixToPostfix(const string& s) {
        stack<string> st;
        for (int i = (int)s.size() - 1; i >= 0; i--) {
            char c = s[i];
            if (isalnum(static_cast<unsigned char>(c))) {
                st.push(string(1, c));
            } else {
                string left  = st.top(); st.pop();   // backwards scan => top is LEFT
                string right = st.top(); st.pop();
                st.push(left + right + c);
            }
        }
        return st.top();
    }
};
```

### Java
```java
import java.util.*;

class Solution {
    public String prefixToPostfix(String s) {
        Deque<String> st = new ArrayDeque<>();
        for (int i = s.length() - 1; i >= 0; i--) {
            char c = s.charAt(i);
            if (Character.isLetterOrDigit(c)) {
                st.push(String.valueOf(c));
            } else {
                String left = st.pop();     // top is the LEFT operand
                String right = st.pop();
                st.push(left + right + c);
            }
        }
        return st.peek();
    }
}
```

### Python
```python
class Solution:
    def prefixToPostfix(self, s: str) -> str:
        st = []
        for c in reversed(s):
            if c.isalnum():
                st.append(c)
            else:
                left = st.pop()           # backwards scan => top is LEFT
                right = st.pop()
                st.append(left + right + c)
        return st[-1]
```

## Key Takeaways
- Scan direction is decided by where the operands sit: prefix → scan right to left, postfix → scan left to right.
- In prefix problems the first pop is the **left** operand; in postfix problems it is the **right** one. Test with `-` or `/` — `+` and `*` hide the bug.
- All four "convert between the bracket-free forms" problems share one skeleton; only the join order (`left+right+op` vs `op+left+right`) differs.
- Both notations are self-delimiting, which is why no brackets and no precedence table are ever needed here.
