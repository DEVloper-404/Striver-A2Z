# Lemonade Change

**Difficulty:** Easy  ·  **Topic:** Greedy Algorithms [Easy, Medium/Hard] › Easy Problems

## Problem
You sell lemonade for `$5` a cup. Customers queue up and each buys exactly one cup, paying with a single `$5`, `$10`, or `$20` bill. You start with no change and must give correct change to every customer immediately, using only bills collected from earlier customers. Return `true` if you can serve everyone, `false` otherwise.

```
Input:  bills = [5, 5, 5, 10, 20]
Output: true
```
The first three customers need no change; the fourth pays $10 and takes a $5 back; the fifth pays $20 and takes a $10 + a $5.

## Approach 1: Track every bill and search for a valid change set
You could store all collected bills in a multiset and, for each customer needing change, search for any subset summing to the required amount. That is correct but hugely over-engineered: the amounts involved are only `$5` and `$15`, and the denominations are only `$5` and `$10`, so a subset search is doing exponential work to answer a question with at most two possible shapes.

- **Time:** exponential in the number of stored bills
- **Space:** O(n)

## Approach 2: Count $5 and $10 bills, prefer paying with $10 (Optimal)
**What actually needs deciding.** Only two counters matter — how many `$5` bills and how many `$10` bills you hold. A `$20` bill is never useful as change (no customer is ever owed `$20` or more), so you do not even need to count them.

Per customer:
- pays **$5** → change owed is 0. Just take the bill: `five++`.
- pays **$10** → change owed is `$5`. There is exactly one way to make it: one `$5`. If `five == 0`, fail. Otherwise `five--, ten++`.
- pays **$20** → change owed is `$15`, and there are two ways: one `$10` + one `$5`, or three `$5`. **Always prefer `$10 + $5`.**

**Why preferring the $10 is correct.** A `$10` bill can only ever be spent as change for a `$20` customer. A `$5` bill can be spent as change for either a `$10` or a `$20` customer, so it is strictly more flexible. Handing over `10 + 5` consumes one rigid bill and one flexible one; handing over `5 + 5 + 5` consumes three flexible ones and hoards a bill that may never be usable. Formally, if some optimal run pays a `$20` customer with three `$5` while a `$10` is in the drawer, rewriting that payment as `10 + 5` leaves the drawer with two extra `$5` and one fewer `$10` — and since every future demand that a `$10` can satisfy (`$15`) can also be satisfied by two of those `$5` plus the third, the rewritten run still succeeds. So the greedy choice never turns a feasible run into an infeasible one.

If neither combination is available, return `false` immediately — no later customer can add change retroactively.

**Dry run on `[5, 5, 5, 10, 20]`:**

| Customer | Bill | Action | five | ten |
|---|---|---|---|---|
| 1 | 5 | take | 1 | 0 |
| 2 | 5 | take | 2 | 0 |
| 3 | 5 | take | 3 | 0 |
| 4 | 10 | give one $5 | 2 | 1 |
| 5 | 20 | give $10 + $5 | 1 | 0 |

Everyone is served → `true`.

Contrast `[5, 5, 10, 10, 20]`: after two `$10` customers you hold `five = 0, ten = 2`. The `$20` customer needs `$15`; you have no `$5` at all, and two `$10` cannot make `$15` → `false`.

- **Time:** O(n) — one pass, O(1) work per customer.
- **Space:** O(1) — two integer counters.

## Code (Optimal)

### C++
```cpp
#include <vector>
using namespace std;

class Solution {
public:
    bool lemonadeChange(vector<int>& bills) {
        int five = 0, ten = 0;
        for (int b : bills) {
            if (b == 5) {
                five++;
            } else if (b == 10) {
                if (five == 0) return false;
                five--;
                ten++;
            } else {                    // b == 20, owe 15
                if (ten > 0 && five > 0) {   // prefer 10 + 5
                    ten--;
                    five--;
                } else if (five >= 3) {      // fall back to 5 + 5 + 5
                    five -= 3;
                } else {
                    return false;
                }
            }
        }
        return true;
    }
};
```

### Python
```python
from typing import List

class Solution:
    def lemonadeChange(self, bills: List[int]) -> bool:
        five = ten = 0
        for b in bills:
            if b == 5:
                five += 1
            elif b == 10:
                if five == 0:
                    return False
                five -= 1
                ten += 1
            else:                       # b == 20, owe 15
                if ten > 0 and five > 0:      # prefer 10 + 5
                    ten -= 1
                    five -= 1
                elif five >= 3:               # fall back to 5 + 5 + 5
                    five -= 3
                else:
                    return False
        return True
```

## Key Takeaways
- The greedy rule is "spend the least flexible bill first": a `$10` is only ever useful for a `$20` customer, while a `$5` is useful for both, so give the `$10` away whenever you can.
- `$20` bills are never given as change, so they need no counter at all — a nice reminder to model only the state that affects future decisions.
- The order of the checks matters: test `ten > 0 && five > 0` before the three-fives fallback, or the greedy property is lost.
- Failing fast is correct — change can only come from bills already collected, so once you cannot pay, no future customer helps.
