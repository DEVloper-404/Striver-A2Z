# Postfix to Prefix Conversion

**Difficulty:** Medium  ·  **Topic:** Stack and Queues [Learning, Pre-In-Post-fix, Monotonic Stack, Implementation] › Prefix, Infix, PostFix Conversion Problems

## Problem
Given a valid **postfix** expression (operator after its two operands), produce the equivalent **prefix** expression (operator before its two operands). Neither form uses brackets. Operands are single characters; operators are `+ - * / ^`.

```
Input:  ab*c+
Output: +*abc
```
Both strings describe the tree `+( *(a, b), c )`, i.e. `(a*b)+c`.

## Approach 1: Postfix → infix → prefix
You could convert postfix to a fully bracketed infix string first, then run infix-to-prefix on it. That works, but it is two non-trivial passes and the intermediate string is longer than either endpoint because of all the added brackets. It also reintroduces precedence handling that neither of the bracket-free notations needs.

- **Time:** O(n^2) with string concatenation
- **Space:** O(n^2)

## Approach 2: One stack pass, joining sub-expressions (Optimal)
The two notations share a decisive property: **both are read in the order operands complete**, and neither needs brackets, because in each of them the position of the operator relative to its operands is fixed. So the conversion never has to think about precedence — it only has to re-glue pieces.

Push finished sub-expressions (as strings, already in *prefix* form) onto a stack:

1. **Operand** → push it as a one-character string; a lone operand is a valid prefix expression.
2. **Operator `op`** → the two most recently finished sub-expressions are its operands. Pop once for `right` (the top of the stack was pushed later, so it is the second operand) and again for `left`. Push `op + left + right` — the operator first, then its two operands, which is exactly prefix form.
3. After the scan the stack holds one string: the answer.

**Why no brackets are needed.** Prefix is self-delimiting: reading left to right, an operator always consumes the next two complete prefix expressions, and there is exactly one way to split the remaining characters. Concatenating `op + left + right` therefore cannot create an ambiguity, no matter how the sub-expressions were built.

**The pop-order trap.** For `ab-`, `a` is pushed first and `b` second, so the first pop is `b`. Writing `op + first_pop + second_pop` would give `-ba` = `b - a`, silently wrong for `-`, `/`, and `^` while looking right for `+` and `*`.

**Dry run on `ab*c+`:**

| Read | Action | Stack (bottom → top) |
|---|---|---|
| `a` | push | `a` |
| `b` | push | `a`, `b` |
| `*` | right=`b`, left=`a` → `*ab` | `*ab` |
| `c` | push | `*ab`, `c` |
| `+` | right=`c`, left=`*ab` → `+*abc` | `+*abc` |

A longer check: `abc/-ak/l-*` (the postfix of `(a - b/c) * (a/k - l)`) walks through as `a`, `b`, `c` → `/` gives `/bc` → `-` gives `-a/bc` → `a`, `k` → `/` gives `/ak` → `l` → `-` gives `-/akl` → `*` gives `*-a/bc-/akl`, which is the correct prefix form.

- **Time:** O(n^2) worst case owing to repeated string concatenation (O(n) stack operations, each copying up to O(n) characters).
- **Space:** O(n^2) worst case for the accumulated strings.

## Code (Optimal)

### C++
```cpp
#include <string>
#include <stack>
#include <cctype>
using namespace std;

class Solution {
public:
    string postfixToPrefix(const string& s) {
        stack<string> st;
        for (char c : s) {
            if (isalnum(static_cast<unsigned char>(c))) {
                st.push(string(1, c));
            } else {
                string right = st.top(); st.pop();   // pushed later => second operand
                string left  = st.top(); st.pop();
                st.push(string(1, c) + left + right);
            }
        }
        return st.top();
    }
};
```

### Java
```java
import java.util.*;

class Solution {
    public String postfixToPrefix(String s) {
        Deque<String> st = new ArrayDeque<>();
        for (char c : s.toCharArray()) {
            if (Character.isLetterOrDigit(c)) {
                st.push(String.valueOf(c));
            } else {
                String right = st.pop();
                String left = st.pop();
                st.push(c + left + right);
            }
        }
        return st.peek();
    }
}
```

### Python
```python
class Solution:
    def postfixToPrefix(self, s: str) -> str:
        st = []
        for c in s:
            if c.isalnum():
                st.append(c)
            else:
                right = st.pop()          # pushed later => second operand
                left = st.pop()
                st.append(c + left + right)
        return st[-1]
```

## Key Takeaways
- Postfix scans left to right; the stack always holds completed sub-expressions in left-to-right order, so an operator simply pops two and re-joins them.
- The join pattern is the only thing that changes between the three targets: `op+left+right` for prefix, `left+right+op` for postfix, `"("+left+op+right+")"` for infix.
- First pop = right operand. This is the single most common bug in all six conversion problems.
- Neither postfix nor prefix needs brackets, so precedence and associativity never enter this conversion at all.
