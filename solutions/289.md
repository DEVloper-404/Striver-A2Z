# Frog jump with K distances

**Difficulty:** Medium  ·  **Topic:** Dynamic Programming [Patterns and Problems] › 1D DP

## Problem
Same setup as the classic Frog Jump, but the frog is stronger: from stone `i` it may jump to any of `i+1, i+2, …, i+k`. A jump from `i` to `j` costs `|height[i] - height[j]|`. Starting on stone `0`, return the minimum total energy to reach stone `n-1`.

```
Input:  n = 5, k = 3, height = [10, 30, 40, 50, 20]
Output: 30
        Best route 0 → 1 → 4 : |30-10| + |20-30| = 20 + 10 = 30
```

## Approach 1: Recursion over all jump lengths (brute force)

**The recurrence.** Let `f(i)` be the minimum energy needed to reach stone `i`. Whatever the optimal route is, its final jump landed on `i` from some stone `i-j` with `1 <= j <= k` (and `i-j >= 0`). The cost of that last jump, `|h[i] - h[i-j]|`, does not depend on how the frog reached `i-j`, so the best route through `i-j` costs exactly `f(i-j) + |h[i] - h[i-j]|`. Minimising over all legal `j`:

```
f(0) = 0
f(i) = min over j = 1..k, i-j >= 0  of  f(i-j) + |h[i] - h[i-j]|
```

Compared to the `k = 2` version, the only change is that each state now has up to `k` incoming branches instead of 2. Written as raw recursion the tree has branching factor `k`, so the cost explodes to roughly `O(k^n)`.

An important detail: the `i-j >= 0` guard must not be silently skipped. If you allow a negative index, or treat the missing branch as cost `0`, you get wrong (too small) answers. Use a large sentinel like `INT_MAX` for illegal branches and never add to it — compare first, or use a value like `1e9` that survives an addition without overflowing.
- **Time:** O(k^n)
- **Space:** O(n) recursion stack

## Approach 2: Memoization
The state is still a single index `i`, so there are only `n` distinct states. Cache `f(i)` in `dp[i]`. Each state now costs `O(k)` work (the loop over jump sizes) instead of `O(1)`, so the total is `O(n·k)`.
- **Time:** O(n·k)
- **Space:** O(n) table + O(n) recursion stack

## Approach 3: Tabulation (Optimal)

Fill the table left to right. When we compute `dp[i]`, every state it needs (`dp[i-1] … dp[i-k]`) already holds its final value, because all of them have a smaller index.

**Algorithm.**
1. `dp[0] = 0`.
2. For `i = 1 … n-1`:
   - set `best = INF`
   - for `j = 1 … k`: if `i - j >= 0`, compute `cost = dp[i-j] + |h[i] - h[i-j]|` and keep `best = min(best, cost)`
   - `dp[i] = best`
3. Return `dp[n-1]`.

**Dry run on `h = [10, 30, 40, 50, 20]`, `k = 3`.**

| i | candidates (from `i-1`, `i-2`, `i-3`) | dp[i] |
|---|---|---|
| 0 | — | 0 |
| 1 | dp[0]+\|30−10\| = 20 | **20** |
| 2 | dp[1]+\|40−30\| = 30 · dp[0]+\|40−10\| = 30 | **30** |
| 3 | dp[2]+\|50−40\| = 40 · dp[1]+\|50−30\| = 40 · dp[0]+\|50−10\| = 40 | **40** |
| 4 | dp[3]+\|20−50\| = 70 · dp[2]+\|20−40\| = 50 · dp[1]+\|20−30\| = 30 | **30** |

Answer `dp[4] = 30`, achieved by `0 → 1 → 4`. Note how at `i = 4` the *longest* legal jump won — another reminder that a greedy "always take the cheapest immediate hop" rule is wrong.
- **Time:** O(n·k)
- **Space:** O(n)

**Can we drop the array?** Not to O(1) as in the `k = 2` case: `dp[i]` looks back across a window of `k` values, so we would need `k` rolling variables, i.e. a deque of size `k` — the same `O(k)` memory. Since `k <= n`, the plain `O(n)` array is simpler and no worse. (A monotonic-deque trick does *not* apply here either, because the term being minimised, `dp[i-j] + |h[i]-h[i-j]|`, depends on `i` through the absolute value and cannot be split into a fixed key.)

## Code (Optimal)

### C++
```cpp
#include <vector>
#include <climits>
#include <cmath>
using namespace std;

class Solution {
public:
    int frogJumpK(int n, int k, vector<int>& height) {
        if (n <= 1) return 0;
        vector<int> dp(n, 0);
        for (int i = 1; i < n; i++) {
            int best = INT_MAX;
            for (int j = 1; j <= k; j++) {
                if (i - j < 0) break;                       // no more legal sources
                int cost = dp[i - j] + abs(height[i] - height[i - j]);
                best = min(best, cost);
            }
            dp[i] = best;
        }
        return dp[n - 1];
    }
};
```

```python
from typing import List


class Solution:
    def frogJumpK(self, n: int, k: int, height: List[int]) -> int:
        if n <= 1:
            return 0
        dp = [0] * n
        for i in range(1, n):
            best = float("inf")
            for j in range(1, k + 1):
                if i - j < 0:
                    break                                    # no more legal sources
                cost = dp[i - j] + abs(height[i] - height[i - j])
                best = min(best, cost)
            dp[i] = best
        return dp[n - 1]
```

## Key Takeaways
- Generalising "1 or 2 steps" to "1..k steps" changes only the transition: one `min` over `k` predecessors instead of over 2. The state stays a single index.
- Complexity goes from O(n) to O(n·k) — states × work per state, the standard way to read a DP's cost.
- Break out of the inner loop as soon as `i - j < 0`; never let an illegal branch contribute a `0` cost.
- Space cannot be reduced below O(k) here because the window of dependencies has width `k`, so the O(n) table is the practical choice.
- The `k = 2` case is exactly the classic Frog Jump; use this version as the mental template for "last move had several possible lengths" problems.
