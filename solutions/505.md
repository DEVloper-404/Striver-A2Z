# Course Schedule II

**Difficulty:** Medium  ·  **Topic:** Graphs [Concepts & Problems] › Topo Sort and Problems

## Problem
There are `numCourses` courses labelled `0..numCourses-1`, and a list `prerequisites` where `[a, b]` means course `b` must be finished before course `a`. Return **any valid order** in which all courses can be taken. If no such order exists, return an empty array.

```
Input:  numCourses = 4, prerequisites = [[1,0], [2,0], [3,1], [3,2]]
Output: [0, 1, 2, 3]      // [0, 2, 1, 3] is equally valid

Input:  numCourses = 2, prerequisites = [[1,0], [0,1]]
Output: []                // circular dependency
```

## Approach 1: Repeatedly scan for an available course
Keep a "done" set. Sweep all courses; take any course whose prerequisites are all done, append it, mark done, and repeat the sweep until a full pass adds nothing. If everything is done, return the order; otherwise return `[]`. This is correct — it is exactly the definition — but each sweep costs O(V + E) and there can be V sweeps.

- **Time:** O(V · (V + E))
- **Space:** O(V)

## Approach 2: Kahn's algorithm — the same idea with O(1) availability checks (Optimal)

**Key observation.** The brute force wastes time re-checking courses whose prerequisites have not changed. A course only becomes newly available at the exact moment its *last* prerequisite is completed. So instead of rescanning, keep a counter `indeg[c]` = number of unfinished prerequisites of `c`, and update it lazily: when a course is completed, decrement the counter of each course that depended on it. A course becomes available precisely when its counter reaches 0, and we can push it onto a queue right then.

That turns "find the next available course" from a scan into a queue pop.

**Algorithm.**
1. Build `graph[b] -> a` for each pair `[a, b]`, and `indeg[a]++`.
2. Enqueue every course with `indeg == 0`.
3. While the queue is non-empty: pop `u`, append it to `order`, and for each dependent `v` do `indeg[v]--`, pushing `v` when the counter hits 0.
4. If `order.size() == numCourses` return `order`, else return `[]` — a short order means some courses were locked in a cycle and never became available.

**Why the output is valid.** A course is appended only after every one of its prerequisites was already appended (that is the only way its counter reached 0). So for every edge `b -> a`, `b` precedes `a` in `order`. Every course is enqueued at most once, so `order` has no duplicates.

**Dry run** on `numCourses = 4`, `[[1,0],[2,0],[3,1],[3,2]]`. Edges: `0->1, 0->2, 1->3, 2->3`. In-degrees: `0:0, 1:1, 2:1, 3:2`.
- Queue `[0]`. Pop 0 → order `[0]`; `indeg[1] = 0` push 1, `indeg[2] = 0` push 2. Queue `[1,2]`.
- Pop 1 → order `[0,1]`; `indeg[3]` = 1, not ready.
- Pop 2 → order `[0,1,2]`; `indeg[3]` = 0 → push 3.
- Pop 3 → order `[0,1,2,3]`. Size 4 = numCourses → return it. Course 3 correctly waited for both 1 and 2.

For `[[1,0],[0,1]]`, both in-degrees are 1, the queue starts empty, `order` is empty and `0 != 2`, so we return `[]`.

- **Time:** O(V + E)
- **Space:** O(V + E)

*(A DFS variant also works: run a DFS topological sort while checking for back edges; if a back edge is found return `[]`, otherwise return the reversed finish order. Kahn's is preferred here because the "did everything fit?" check is a single size comparison.)*

## Code (Optimal)

### C++
```cpp
#include <vector>
#include <queue>
using namespace std;

class Solution {
public:
    vector<int> findOrder(int numCourses, vector<vector<int>>& prerequisites) {
        vector<vector<int>> graph(numCourses);
        vector<int> indeg(numCourses, 0);
        for (auto& p : prerequisites) {
            graph[p[1]].push_back(p[0]);     // prerequisite -> course
            indeg[p[0]]++;
        }

        queue<int> q;
        for (int i = 0; i < numCourses; i++)
            if (indeg[i] == 0) q.push(i);

        vector<int> order;
        order.reserve(numCourses);
        while (!q.empty()) {
            int u = q.front(); q.pop();
            order.push_back(u);
            for (int v : graph[u]) {
                if (--indeg[v] == 0) q.push(v);
            }
        }
        if ((int)order.size() != numCourses) return {};
        return order;
    }
};
```

### Java
```java
import java.util.*;

class Solution {
    public int[] findOrder(int numCourses, int[][] prerequisites) {
        List<List<Integer>> graph = new ArrayList<>();
        for (int i = 0; i < numCourses; i++) graph.add(new ArrayList<>());
        int[] indeg = new int[numCourses];
        for (int[] p : prerequisites) {
            graph.get(p[1]).add(p[0]);
            indeg[p[0]]++;
        }

        Queue<Integer> q = new ArrayDeque<>();
        for (int i = 0; i < numCourses; i++)
            if (indeg[i] == 0) q.add(i);

        int[] order = new int[numCourses];
        int idx = 0;
        while (!q.isEmpty()) {
            int u = q.poll();
            order[idx++] = u;
            for (int v : graph.get(u)) {
                if (--indeg[v] == 0) q.add(v);
            }
        }
        return idx == numCourses ? order : new int[0];
    }
}
```

### Python
```python
from collections import deque
from typing import List

class Solution:
    def findOrder(self, numCourses: int, prerequisites: List[List[int]]) -> List[int]:
        graph = [[] for _ in range(numCourses)]
        indeg = [0] * numCourses
        for course, need in prerequisites:
            graph[need].append(course)
            indeg[course] += 1

        q = deque(i for i in range(numCourses) if indeg[i] == 0)
        order: List[int] = []
        while q:
            u = q.popleft()
            order.append(u)
            for v in graph[u]:
                indeg[v] -= 1
                if indeg[v] == 0:
                    q.append(v)

        return order if len(order) == numCourses else []
```

## Key Takeaways
- Course Schedule II is Course Schedule I plus recording the pop order — the topological ordering *is* the study plan.
- The in-degree counter replaces repeated "are my prerequisites done?" scans, cutting O(V·(V+E)) to O(V+E).
- `len(order) < numCourses` is the cycle signal; return `[]` then, do not return a partial order.
- Multiple valid answers exist; use a min-heap instead of a queue only if the problem demands the lexicographically smallest one.
