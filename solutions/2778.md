# Floor in a Binary Search Tree

**Difficulty:** Easy  ·  **Topic:** Binary Search Trees [Concept and Problems] › Practice Problems

## Problem
Given the root of a BST and an integer `key`, return the **floor** of `key`: the largest value present in the tree that is less than or equal to `key`. If every value in the tree is greater than `key`, return `-1`.

```
Input:  tree = [10, 5, 13, 3, 7, 11, 15], key = 8
Output: 7        (values ≤ 8 are {3, 5, 7}; the largest is 7)

Input:  tree = [10, 5, 13, 3, 7, 11, 15], key = 2
Output: -1       (no value is ≤ 2)
```

## Approach 1: Brute Force (inorder traversal + scan)
An inorder traversal of a BST produces the values in sorted order. Collect them into an array, then take the last element that is `<= key` (a linear scan, or a binary search on the sorted array).

It works, but it reads every node and allocates an array of size N, even though the answer is decided by comparisons along a single path.
- **Time:** O(N)
- **Space:** O(N)

## Approach 2: Optimal (guided descent, remembering the best candidate)
The whole problem hinges on one observation about the BST invariant:

> If a node's value `v` is **greater than** `key`, then `v` is not a valid floor, and neither is anything in `v`'s right subtree — every node there is even larger. So the entire right subtree plus `v` can be thrown away in one move.
>
> If a node's value `v` is **less than or equal to** `key`, then `v` *is* a valid answer. Could there be a better (larger) one? Only in `v`'s right subtree, because every node in the left subtree is smaller than `v`. So record `v` and descend right.

That gives a simple loop: keep a variable `best`, start at the root, and at every node either record-and-go-right or just go-left. When you fall off the tree, `best` holds the answer. Since we only ever move downward, the loop runs at most `H` times.

Why is `best` guaranteed to be the maximum such value? Every time we overwrite `best`, we move into the right subtree of the old `best`, so every subsequent candidate is strictly larger than the one it replaces. And we never skip past a better candidate: we only prune subtrees that are provably all `> key` (the right subtree of a too-large node) or all smaller than a candidate we already recorded (the left subtree of a recorded node).

**Dry run** on `[10, 5, 13, 3, 7, 11, 15]` with `key = 8`:

| Node | Compare | Action | best |
|------|---------|--------|------|
| 10 | 10 > 8 | prune 10 and its right subtree, go left | -1 |
| 5  | 5 ≤ 8  | record, go right | 5 |
| 7  | 7 ≤ 8  | record, go right | 7 |
| null | — | stop | **7** |

Answer `7`, matching the brute force.

The same loop naturally handles the exact-match case: if `cur->val == key` we record it and go right, but nothing in the right subtree can be `<= key`, so the loop just falls through and returns `key`. (You can also `return` immediately as a small optimisation.)
- **Time:** O(H) — O(log N) on a balanced tree, O(N) on a skewed one
- **Space:** O(1) with the iterative version

## Code (Optimal)

### C++
```cpp
// struct TreeNode { int val; TreeNode *left, *right; TreeNode(int x) ... } — standard definition

class Solution {
public:
    int floorInBST(TreeNode* root, int key) {
        int best = -1;
        TreeNode* cur = root;
        while (cur != nullptr) {
            if (cur->val == key) return cur->val;   // exact match: cannot be beaten
            if (cur->val < key) {
                best = cur->val;                    // candidate; a bigger one can only be on the right
                cur = cur->right;
            } else {
                cur = cur->left;                    // too large; whole right subtree is too large too
            }
        }
        return best;
    }
};
```

```python
class Solution:
    def floorInBST(self, root, key):
        best = -1
        cur = root
        while cur:
            if cur.val == key:
                return cur.val
            if cur.val < key:
                best = cur.val        # valid answer so far; try to improve on the right
                cur = cur.right
            else:
                cur = cur.left        # too big; prune this node and its right subtree
        return best
```

## Key Takeaways
- Floor search is binary search on a tree: each comparison eliminates one subtree, so the cost is the height, not the node count.
- Track the best candidate as you descend — the answer is usually *not* the node you stop at, it is the last valid node you passed through.
- The iterative form uses O(1) extra space; the recursive form is equally correct but pays O(H) stack.
- Watch the "no answer" case: if `key` is below the minimum you never record anything and must return `-1`.
