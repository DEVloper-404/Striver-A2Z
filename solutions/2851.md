# Longest Increasing Subsequence |(DP-43)

**Difficulty:** Medium  ·  **Topic:** Dynamic Programming [Patterns and Problems] › DP on LIS

## Problem
Given an array `arr`, return the length of its longest strictly increasing subsequence, but do it in **O(n log n)** rather than the classic O(n²) DP. This is the "patience sorting" formulation of LIS, and it is the version you want when `n` is large (10^5 or more).

```
Input:  arr = [1, 7, 8, 4, 5, 6, -1, 9]
Output: 5      (the subsequence [1, 4, 5, 6, 9])
```

## Approach 1: Why the O(n²) DP is not enough
The standard recurrence `dp[i] = 1 + max{dp[j] : j < i, arr[j] < arr[i]}` scans every earlier index for every `i`. What that inner loop is really asking is: *"among all elements before `i` that are smaller than `arr[i]`, what is the best chain length?"* That is a range-query, and answering it by linear scan is what costs O(n²). The O(n log n) method answers the same question with a binary search instead.

- **Time:** O(n²)
- **Space:** O(n)

## Approach 2: Maintain the smallest tail per length (Optimal)
Build an array `tails`, where

> `tails[k]` = the **smallest value** that can be the last element of an increasing subsequence of length `k + 1`, considering only the elements processed so far.

Two properties make this work, and both are worth understanding rather than memorising:

**Property 1 — `tails` is strictly increasing.** Any increasing subsequence of length `k+1` contains, as a prefix, an increasing subsequence of length `k` whose last element is strictly smaller. So the best (smallest) tail achievable at length `k` is strictly less than the best tail at length `k+1`. Being sorted is exactly what licenses the binary search.

**Property 2 — keeping only the smallest tail loses nothing.** If two chains both have length `k` and one ends in a smaller value, every future element that can extend the larger-tailed chain can also extend the smaller-tailed one. The smaller tail *dominates*, so it is safe to forget the other.

The algorithm is then one pass:

1. For each `x`, binary search `tails` for the first position `pos` with `tails[pos] >= x` (`lower_bound` / `bisect_left`).
2. If `pos == len(tails)`, then `x` is larger than every tail — it extends the longest chain found so far, so **append** it and the answer grows by one.
3. Otherwise **overwrite** `tails[pos] = x`. The length of that chain does not change, but its tail just got smaller, which can only help future elements.

The answer is `len(tails)`.

**Dry run** on `[1, 7, 8, 4, 5, 6, -1, 9]`:

| x  | pos | action  | tails after        |
|----|-----|---------|--------------------|
| 1  | 0   | append  | [1]                |
| 7  | 1   | append  | [1, 7]             |
| 8  | 2   | append  | [1, 7, 8]          |
| 4  | 1   | replace | [1, 4, 8]          |
| 5  | 2   | replace | [1, 4, 5]          |
| 6  | 3   | append  | [1, 4, 5, 6]       |
| −1 | 0   | replace | [−1, 4, 5, 6]      |
| 9  | 4   | append  | [−1, 4, 5, 6, 9]   |

Length `5`. Notice the final `tails` is `[-1, 4, 5, 6, 9]`, which is **not** a subsequence of the input — `-1` appears after `6` in `arr`. This is the standard gotcha: the array's *length* is the answer, its *contents* are not the answer. Replacing `1` by `-1` cost nothing and would have paid off had a `0` appeared later.

Why "patience sorting"? Imagine dealing cards into piles where a card may only be placed on a pile whose top card is `>= it`, always choosing the leftmost legal pile. `tails` is the list of pile tops, and the number of piles equals the LIS length.

- **Time:** O(n log n) — one binary search per element
- **Space:** O(n)

## Approach 3: Variants worth knowing
The same skeleton solves nearby problems by changing only the search predicate:

- **Longest non-decreasing subsequence** (duplicates allowed): use `upper_bound` / `bisect_right`, so an equal value appends instead of replacing.
- **Longest decreasing subsequence**: negate every element and run the same code.
- **Printing the subsequence**: `tails` alone is insufficient; track `tailsIdx[k]` (the array index of each tail) plus a `parent[]` array, then backtrack.

- **Time:** O(n log n)
- **Space:** O(n)

## Code (Optimal)

### C++
```cpp
#include <vector>
#include <algorithm>
using namespace std;

class Solution {
public:
    int longestIncreasingSubsequence(vector<int>& arr) {
        vector<int> tails;   // tails[k] = smallest tail of an increasing subsequence of length k+1
        for (int x : arr) {
            auto it = lower_bound(tails.begin(), tails.end(), x);
            if (it == tails.end()) tails.push_back(x);  // x extends the longest chain
            else *it = x;                               // x becomes a better tail for that length
        }
        return (int)tails.size();
    }
};
```

### Java
```java
class Solution {
    public int longestIncreasingSubsequence(int[] arr) {
        int n = arr.length;
        int[] tails = new int[n];
        int size = 0;
        for (int x : arr) {
            int lo = 0, hi = size;            // first index with tails[idx] >= x
            while (lo < hi) {
                int mid = (lo + hi) >>> 1;
                if (tails[mid] < x) lo = mid + 1;
                else hi = mid;
            }
            tails[lo] = x;
            if (lo == size) size++;
        }
        return size;
    }
}
```

### Python
```python
from bisect import bisect_left
from typing import List


class Solution:
    def longestIncreasingSubsequence(self, arr: List[int]) -> int:
        tails = []
        for x in arr:
            pos = bisect_left(tails, x)   # first index where tails[pos] >= x
            if pos == len(tails):
                tails.append(x)
            else:
                tails[pos] = x
        return len(tails)
```

## Key Takeaways
- `tails[k]` is the smallest achievable tail for length `k+1`; it stays sorted, which is the reason binary search is valid.
- Replacing a tail never changes the answer's length — it only makes a future extension more likely, so the greedy overwrite is safe.
- The contents of `tails` are not a real subsequence; only its size is meaningful.
- `bisect_left`/`lower_bound` → strictly increasing; `bisect_right`/`upper_bound` → non-decreasing. One character of difference, two different problems.
